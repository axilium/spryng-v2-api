## API overview

This API enables you to create a batch message request and then control the throughput so not all messages are sent at the same time. This can be configured to splitting messages into hourly batches, or setting a maximum number of messages to be sent within a timeframe i.e. that day.

Not only does throttling for large batch sends ensure that networks don’t become overwhelmed by large requests, it also allows you to better determine the spread of inbound messaging received from a large outbound message.
There are 2 types of throttling methods available via this API:

- Rate based - control the rate limit of messages to be sent per hour. The platform will then calculate the estimated end date for the request based on the specified rate limit *
- Period based - specify the end date required for all the messages within the request to be sent. The platform then determines the optimal rate limit for the request

*any throttling schedules applied will still adhere to our default API rate limiting policy. All schedule times should be provided in UTC.
Note: once all messages within a thottled schedule have all been accepted to the platform, the throttle schedule will no longer be editable.

If you would like to duplicate a previous throttled schedule, send a GET request using v2/throttle-schedule/{throttleScheduleId} endpoint to gain the required information. If you're missing the throttle-scheduleId for the request you'd like to duplicate, you can view all throttle schedules by calling GET v2/throttle-schedule. The response data can then be copied to a new POST request as required using v2/throttle-schedule.

Before you start using this endpoint, please check you have your Account, API Key and Base URL set up and have familiarised yourself with our implementation prerequisites in our Introduction documentation.

Please note: some countries have specific sending regulations, visit our support site for further information on [territory specific regulations](https://www.productsupport.esendex.com/regulations/). You can set up your SenderIds, STOP/CONTACT auto-responses for French recipients and other regulation configurations in the Esendex portal.

## Request body

You can use the cURL sample provided on the right hand side of this page to directly copy/paste into your chosen integration tool, using the below properties to modify your request as required for your business needs.

**Required, or conditional, request body parameters**

If a required parameter is not provided, or incorrect, the request will fail. If a parameter is Conditional, it is only required for certain channels or is dependent on the desired format of the message.

| Parameter name | Type | Required or Conditional | Description |
| --- | --- | --- | --- |
| throttleScheduleInformation | JSON object | Required | The details of the throttled schedule. Use the below properties to define the schedule requirements alongside the conditional properties required depending on if you’re creating a periodic or rate based schedule |
| throttleScheduleInformation.startDate | String | Required | The start date of the throttle schedule e.g. “YYYY-MM-DD” |
| throttleScheduleInformation.timeSlotStartDate | String | Required | The time the message should be sent provided in ICT format format YYYY-MM-DD:HH:MMZ e.g. 2025-03-05T11:47:25.723Z. The platform operates in UTC time zone exclusively. If you want to schedule a message to correspond to a different time zone |
| throttleScheduleInformation.rateOfsend | Integer | Conditional | The number of messages to be sent per hour. Required if configuring a rate limited scheduled send |
| throttleScheduleInformation.endDate | String | Conditional | The end date of the throttle schedule e.g. “YYYY-MM-DD”. Required if configuring a periodic scheduled send |
| throttleScheduleInformation.timeSlotEnd | String | Conditional | The end time of the throttle schedule e.g. “HH:MM:SS”. Must be provided in UTC. Required if configuring a periodic scheduled send |
| dispatch | JSON object | Required | The details of the dispatch settings. Use the below properties to define as required |
| recipients | JSON array | Conditional | The list of recipients for the message request provided as either a list of recipient numbers or by using existing contacts within your address book |
| recipients.msisdn | String | Conditional | The phone number of recipient |
| contacts | JSON array | Conditional | Can contain an array of contacts. Each contact must correspond to a contactId that belongs to the account which is sending the message. Using contactIds allow the data in each contact's custom fields to be used as variables in the message body |
| cotacts.contactId | JSON array | Conditional | Required when using "contacts". The contactId of the contact(s) you wish to send a message to. A max of 50000 contacts can be included in a single request |

**Optional request body parameters**

These parameters are not mandatory within the request body, they are designed to provide you further capability to customise or filter your requests.

| Parameter | Type | Description |
| --- | --- | --- |
| throttleScheduleInformation.daysOfweek | JSON array | A list of days of the week throttled messages can be sent on. Possible values: Sunday \| Monday \| Tuesday \| Wednesday \| Thursday \| Friday \| Saturday |
| dispatch.characterSet | String | Allowed character sets are: Auto \| GSM \| Unicode e.g.GSM uses a smaller characterSet which allows characters per message part to around 140. Unicode allows using of a large set of special characters and Unicode emojis but reduces characters per message part to around 70. Auto means we will detect the characters provided and use GSM when only GSM characters are present |
| dispatch.messageType | String | Used to help reporting on certain message types. Enum e.g. MarketingAndResearch \| NotificationsAndReminders \| AuthenticationAndSecurity \| PaymentsAndCollections \| InternalOperations \| CustomerSupport \| Conversational |
| dispatch.name | String | Optional friendly name for the request. Will be present message history export and can make some data analysis or grouping easier |
| metaData | JSON object | Can contain "key": "value" pairs. These are saved with the message and will be returned when exporting the message history. This can make some data analysis easier |
| recipients.metaData | string | Additional meta data which can be used to add extra context to recipients |
| recipients.variables | string | Can contain "key": "value" pairs which can be used in the message body. This allowed a common message body to be personalised for each recipient |

In order to shorten a URL within a message, embed [shorten: http://example/longURL.com] into the request "body.text" property. The platform will then automatically convert your long URL into a shortened URL in format uk.endx.io/abcd123. These are unique per recipient. To see an example of this request, see the Request body examples section below. Please note, the shorten URL capability is not available during Trial. You will need to upgrade to a full account to use this feature.
