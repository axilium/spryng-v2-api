## Setting up a bind

An SMPP bind is a request to establish a session or connection for sending one-way or two-way messages. During the bind operation, you'll pass your systemID and password. Once your information is authenticated, a connection is established. With the connection established, you can then send and receive messages.

There are 3 possible bind types:

- Transmitter - a recipient will receive messages but cannot return messages i.e. send only
- Receiver - a sender can receive messages from the server i.e. receive only
- Transceiver - send and receive messages

**Destination address**
We support sending to International numbers only. Valid TON is 1 and NPI of 1.

**Source address**
These may be International, National or Alphanumeric. When International the TON should be 1 and NPI also 1, when National the TON must be 2 and the NPI must be 1, otherwise Alphanumeric must have TON of 5 and NPI of either 1 or 0.

Alphanumerics can contain characters from the following sets:

- Numbers 0 to 9
- Upper and lower case A to Z
- Symbols !"#$%&'*+-./:<=>?@_

## Sending a bind request

A bind request is composed of a header indicating the type of request and Protocol Data Units (PDU) parameters. SMPP defines operations and Protocol Data Units (PDUs), where each operation has a request PDU and a corresponding response PDU.

**Supported PDUs**

- BIND_TRANSMITTER - You send messages on this bind and optionally receive delivery notifications on another bind
- BIND_RECEIVER - You receive delivery notifications on this bind
- BIND_TRANSCEIVER - You both send messages and receive delivery notifications on this bind
- UNBIND - You wish to close your bind to us
- ENQUIRE_LINK - You want to ensure your bind stays connected
- SUBMIT_SM - You are submitting a short message
- DELIVER_SM - We are sending you a delivery notification or received message

For further information on PDU structures and required parameters, please review the [SMPP v3.4 protocol spec](https://smpp.org/SMPP_v3_4_Issue1_2.pdf)

**Mandatory Fields**

service_type, schedule_delivery_time, replace_if_present and default_msg_id are not supported and must be set to default values, e.g. 0 for integers and null for strings.

**Concatenated Messages**
Long messages may be submitted using the 8bit or 16bit UDH mechanism by setting the ESM class to 64. We do not support the sar_msg_ref_num, sar_total_se.g.ments and sar_se.g.ment_seqnum or message_payload optional parameters. All parts must be sent via the same bind and if we detect that all parts are not submitted within a reasonable length of time then a delivery report with a UNDELIV status will be sent for each submitted part. i.e. We will not attempt to deliver to destinations incomplete concatenated messages.

**Windowing**

The window size of the service is 1. Although you may be able to transmit more pending PDUs than that it is highly recommended that you do not. The service will only respond to 1 PDU at a time.

## Delivery reports

Delivery reports (DLRs) will be returned in short message field of deliver_sm PDU:

```
id:{message_id} sub:{message_sub} dlvrd:{message_dlvrd} submit date:{message_submit_date} done date:{message_done_date} stat:{message_stat} err:{message_err}
```

DLRs will contain the receipted_message_id and message_state optional parameters (otherwise known as TLVs).
 In addition the short_message of the PDU will be formatted as described by Appendix B of the SMPP 3.4 specification. The err field provides some additional context to why a message may have been undeliverable as detailed below.
The service will queue DLRs for a period of time if you are not connected with a BIND_RECEIVER or BIND_TRANSCEIVER.

**Registered Delivery**

This can be set to 0 or 1. If you request delivery receipts but do not bind in with either a BIND_RECEIVER or BIND_TRANSCEIVER, delivery reports will be queued with Spryng for 72 hours and then discarded.
The following fields are relevant in the deliver_sm operations when used for transmitting delivery receipts.

| Field | Size (octets) | Description |
| --- | --- | --- |
| id | Variable | The following fields are relevant in the deliver_sm operations when used for transmitting delivery receipts |
| sub | 3 | Number of short messages originally submitted. The value may be padded with leading zeros |
| dlvrd | 3 | Number of short messages delivered. The value may be padded with leading zeros |
| submit_date | 10 | The time and date at which the short message was submitted. The format is:YYMMDDhhmm where:YY = last two digits of the year (00-99) \| MM = month (01-12) \| DD = day (01-31) \| hh = hour (00-23) \| mm = minute (00-59) |
| done_date | 10 | The time and date at which the short message reached it’s final state. The format is the same as for the submit date |
| stat | 7 | The final status of the message. See Message states below. State text may be abbreviated |
| err | 3 | A network or SMSC error code for the message. See Error codes below |
| text | 20 | Unused field |

## Rate limits

No more than 5 submit_sm PDUs will be processed per second per transmitting session. If you exceed this rate the service will respond with the standard ESME_RTHOTTLED (0x58) PDU response code, and the submission will not be processed further. Throttled messages should be re-transmitted to be processed. You should ensure you have implemented flow control to avoid receiving this response.The service will send up to 10 DLRs per second per receiving session. This can be configured by sending a request to your account manager.

## Maintaining connections

We recommend that you periodically send an ENQUIRE_LINK on all connections to ensure that connections remain open if required and are not considered idle close idle connections. We recommend this is not less than once every minute and not more than once every 15 seconds.
If no messages are received by the server within one minute, the server will send an ENQUIRE_LINK request to the client. Should this ENQUIRE_LINK return no response, the session will be disconnected from the server.

**Validity Period**
May be specified in relative or absolute validity formats, if not set the Account’s default is used. Relative times should obey the 24 hour clock format, if not the default will apply.
